Assignment 1: A video call application

CS 456, Fall 2026

Released Tue, Oct 6 · Due Wed, Oct 28, 11:59 pm

In this assignment, you will build a simple video call application. In a real video conferencing application, many users can join a call and talk at the same time. For this assignment, we have simplified that to two users. Only one of them, the sender, has their video on, and the goal is to play the sender's video, live, for the other user, the receiver. We have also left out audio.

In class, we have talked at length about web applications and on-demand video streaming, and about video calls too. What makes a video call different is that it happens in real time. A web page can take an extra second to load, and an on-demand video player can buffer several seconds ahead. In a call, a frame that shows up more than 200 ms after it was captured is too late to be useful. A video call application needs to deliver frames in time, even when the network loses packets or its throughput and latency change in the middle of the call.

We have also discussed how transport protocols can help applications deal with an unreliable network whose conditions change. Most existing network stacks provide two options for transport. One is bare-bones, like UDP. It does not do segmentation and reassembly, and it is best effort (for example, it does not recover lost packets). You give it a piece of your data, already chunked to fit in one packet, and if that chunk makes it to the receiver, it is delivered to the right application on the destination computer. The other gives the application a fully reliable byte stream, like TCP. As we discussed in class, the latter does not quite fit a video call, so most video call applications use the bare-bones one and deal with loss and with changes in delay and rate in the application itself. That is what you will do in this assignment, over a simulated network, as a way to practice what we learned in Part 1.

2. The simulator

Interacting with the simulated network. To interact with the simulated network, your sender and receiver receive a net object:

  • Sending a packet: net.send(pkt: bytes) sends pkt, at most 1500 bytes long, to the other side.
  • Reacting to a received packet: when a packet arrives, the simulator calls the on_packet(pkt) method of the corresponding Receiver, Sender, or setup class.

The simulated link. The link is bidirectional, meaning the two directions of the link work simultaneously. Packets going one way never wait behind packets going the other way. We use the same rate and propagation delay for each direction. During the call setup, you will receive the initial rate and the initial round-trip propagation delay (the propagation delay there and back), but they can and will change during the call. Finally, the simulated network will not corrupt or duplicate packets.

When a packet is sent over the simulated link, it will go through the following steps:

  1. Size check. If the packet is larger than 1500 bytes (the MTU), this is due to an error in your code and the run will stop.
  2. Transmission. The link carries packets one at a time at its rate. The time it takes to put a packet onto the link is the packet size divided by the link rate (the transmission delay). If you send faster than the rate, your packets wait in line behind the ones you sent earlier (the waiting delay). If there are too many packets waiting in line, some may get dropped.
  3. Loss. The packet may be dropped. Packet losses can happen in bursts of several packets in a row.
  4. Delay. The packet arrives after the propagation delay plus a random extra delay, different for every packet (jitter). Because of jitter, packets can arrive out of order.

Simulated time and timers. You can access the following methods from the clock module (add import clock at the top of your file):

  • clock.now(): the current simulated time, in ms.
  • clock.set_timer(delay_ms: float, fn): call fn() after delay_ms of simulated time. Returns a timer object. You can call cancel() on it to stop the timer.

Note that the simulator does not simulate processing time. It does not advance time while your code is running, so your code appears to run instantaneously.

3. Part A: Joining the call

To join a call, the receiver needs the call's passcode. It gets the passcode from the join server (which is different from the sender).

Interacting with the join server. The receiver talks to the join server over a reliable byte stream, represented as a stream object:

  • Sending data: stream.send(data: bytes) sends data to the join server.
  • Receiving data: stream.recv(n: int) waits until bytes arrive from the join server, and returns up to n of them. If the join server has closed the stream, it returns b"".

In this case, and only in this part, the transport protocol underlying the stream interface ensures that data is delivered to the other end reliably and in order. Note that a byte stream delivers bytes, not messages. While the join server sends its whole reply at once, the stream may deliver it in several pieces, so one call to stream.recv may return only part of the reply.

The join protocol. The protocol you should adhere to is the following. Each message has the following format: message type, a space, the length of the rest of the message in bytes, a space, and the rest of the message:

client:  JOIN <length> <call>
server:  OK <length> <passcode>
    or   ERR <length> no-such-call

For example, the request to join the call random_loss is JOIN 11 random_loss. A passcode is a string of letters and digits with varying length across calls. It is always short enough to fit in one packet. After sending its reply, the join server closes the stream.

What to implement. Implement the get_passcode function in join.py:

def get_passcode(stream, call): ...
  • call is the name of the call to join.
  • Return the passcode as a string. If the join server replied ERR, or closed the stream before sending a complete reply, return None.
  • When get_passcode returns, the simulator gives the passcode to your ReceiverSetup, which uses it to ask the sender to start the call (Section 4).

What to watch for. Your get_passcode should work however the stream splits up the reply: for example, when the whole reply arrives in one piece, when it arrives one byte at a time, or when it arrives in random-sized pieces with pauses between them. It should also handle an ERR reply, and a stream that closes before the reply is complete.

Testing these cases. To test your code, you can write a test file that makes the join server and the stream behave in these ways, and give it to sim.py with --test:

python3 sim.py scenarios/clean.json --test mytest.json

A test file is a small JSON file, for example {"join": {"reply": "err", "recv_bytes": 1}}. Its join section can have:

  • "reply": "ok" (the default) or "err".
  • "recv_bytes": if this is x, each call to stream.recv returns at most x bytes, for example 1 for one byte at a time. By default, it returns a random number of bytes.
  • "close_after": the join server closes the stream after sending this many bytes of its reply.

4. Part B: Setting up the call

Before the call starts, the sender and receiver do a handshake, to make sure they are both ready and to agree on the call's parameters. You implement the sender's side of the handshake in the SenderSetup class, and the receiver's side in the ReceiverSetup class, both in setup.py.

The setup protocol. The protocol has three message types. Each message fits in one packet. The first byte determines the type of the message, as described below:

MessageSent byMessage format
JOINreceiver0x01 (1 byte), followed by the passcode bytes
ACCEPTsender0x02 (1 byte), followed by the rate in kbps (4 bytes) and the round-trip propagation delay in ms (4 bytes)
CONFIRMreceiver0x03 (1 byte), followed by the same rate (4 bytes) and delay (4 bytes) as in the ACCEPT

The rate and delay are unsigned integers, most significant byte first. You send and receive these messages with net.send and on_packet (Section 2), so remember that any of them can be lost, delayed or reordered on the way.

Your implementation must complete the handshake even when some of these packets are lost. In order for us to test your solution, each side is responsible for the following:

  1. The receiver keeps sending JOIN until an ACCEPT arrives.
  2. The sender replies to every JOIN that has the right passcode with an ACCEPT, and ignores a JOIN with a wrong passcode. Once it has sent an ACCEPT, it keeps sending ACCEPTs until a CONFIRM arrives whose rate and delay match the ACCEPT (rule 4).
  3. The receiver replies to every ACCEPT with a CONFIRM. When it receives the first ACCEPT, your ReceiverSetup calls start_call(rate_kbps, rtt_ms), and the simulator creates your Receiver, which is responsible for handling the actual video call packets. Setup messages keep going to your ReceiverSetup until the first video packet arrives, which shows that a CONFIRM got through. Until then, it should reply to any later ACCEPT with a CONFIRM. Setup messages that arrive for the receiver after that are dropped.
  4. The sender ignores a CONFIRM whose rate and delay do not match its ACCEPT. When it receives the first CONFIRM that matches, your SenderSetup stops sending ACCEPTs and calls start_call(), and the simulator creates your Sender, which is responsible for sending the video, and starts the camera. From then on, the simulator does not give your SenderSetup any more packets, and will drop any setup messages that arrive at the sender.

How you do this, including how long to wait before sending a message again, is up to you.

What to implement. Implement both sides of the protocol in setup.py:

class SenderSetup:
    def __init__(self, net, passcode, rate_kbps, rtt_ms, start_call): ...
    def on_packet(self, pkt): ...

class ReceiverSetup:
    def __init__(self, net, passcode, start_call): ...
    def on_packet(self, pkt): ...
  • SenderSetup is created at time 0, and is given the right passcode and the rate and delay to put in its ACCEPT. Note that these represent the rate and delay values only at the start of the call and can change during the call. The simulator calls its on_packet when a JOIN or CONFIRM arrives. It should call start_call() as described in rule 4 above.
  • ReceiverSetup is created as soon as your get_passcode returns the passcode, and is given that passcode. It should send its first JOIN from __init__, since nothing else calls it until a packet arrives. The simulator calls its on_packet when an ACCEPT arrives. It should call start_call(rate_kbps, rtt_ms) with the values from the first ACCEPT, as described in rule 3 above.
  • The simulator passes setup messages, meaning packets whose first byte is 0x01, 0x02 or 0x03, to the on_packet method of your SenderSetup or ReceiverSetup, and all other packets to the on_packet method of your Sender or Receiver.
  • Calling start_call more than once has no effect after the first time.
  • If the camera has not started within 5 seconds, the simulator marks the call as failed, and no frames are shown.

What to watch for. Make sure you follow the protocol precisely, as we will test your SenderSetup with our own ReceiverSetup, and vice versa. The handshake should complete even when any of the setup messages are lost, including CONFIRM. Your sender's side should never start the call before a matching CONFIRM arrives, and a receiver with the wrong passcode should never get a call started.

Testing these cases. A test file (Section 3) can also have a setup section that makes the handshake face these situations, for example {"setup": {"lose": {"JOIN": 2, "CONFIRM": 1}}}. It can have:

  • "lose": how many of the first JOIN, ACCEPT and CONFIRM messages the network should lose. When a test file has "lose", the network loses only these messages and no other packets.
  • "wrong_passcode": true to give your ReceiverSetup a wrong passcode, so the call should never start.

5. Part C: The call itself

In this part, you implement the sender and receiver logic for transferring the actual video data. You implement the sender's side in the Sender class, and the receiver's side in the Receiver class, both in call.py.

5.1 The video

The sender's side does not have a real camera. Instead, the simulator plays a 30-second excerpt from Big Buck Bunny1, an open animated film, as if a camera were capturing it. Your code and your score do not depend on what the frames show, only on their sizes, so any other video would work the same way.

  • The camera produces 25 frames per second, one every 40 ms.
  • Each frame is available at 4 quality levels, from 0 (lowest) to 3 (highest). The same frame at a higher quality level looks better and is represented with more bytes. Every frame at a given level has the same size: 1500, 3500, 8500 and 17000 bytes for levels 0 to 3. You can also find it with len(frame.data[level]).
  • Your sender decides which level to send for each frame.

A frame object has the following fields:

  • frame.id: the frame's position in the video. The camera numbers frames in the order it captures them: the first frame of the call is 0, the next is 1, and so on.
  • frame.time: when the frame was captured, in ms. You can assume the sender's and receiver's clocks are fully synchronized.
  • frame.data: the frame's data at each quality level. frame.data[level] is the frame at that level, ready to split into packets.

5.2 What to implement

Implement the sender and the receiver in call.py:

class Sender:
    def __init__(self, net, rate_kbps, rtt_ms): ...
    def on_frame(self, frame): ...
    def on_packet(self, pkt): ...

class Receiver:
    def __init__(self, net, rate_kbps, rtt_ms, player): ...
    def on_packet(self, pkt): ...
  • The simulator creates your Sender when your SenderSetup calls start_call(), and your Receiver when your ReceiverSetup calls start_call(rate_kbps, rtt_ms) (Section 4). Each is given the rate and round-trip propagation delay at the start of the call. Note that these are only the values at the start of the call: the rate and the delay can change during the call.
  • The simulator calls your Sender's on_frame(frame) every time the camera has a new frame. It calls your Sender's on_packet(pkt) when a packet from your Receiver arrives, and your Receiver's on_packet(pkt) when a packet from your Sender arrives.
  • Your Receiver can hand a frame to the player with player.show(frame_id, data).
  • You decide what goes in the packets your Sender and Receiver send, both what metadata they carry and the payload. The only restriction is that the first byte must not be 0x01, 0x02 or 0x03, because the simulator uses it to tell setup messages apart.
  • The simulator runs the sender's side (SenderSetup, Sender) and the receiver's side (get_passcode, ReceiverSetup, Receiver) as if they were on separate machines. Each side gets its own copy of your files, so a variable set on one side is not visible on the other, and the two sides can only communicate through the network.
  • Your code should only use what the simulator gives it: its arguments, net, clock, the frames and the packets. For example, it should not open or read any files, such as the scenario files or the video clip.
  • Put all your code in join.py, setup.py and call.py. The simulator only loads these three files, so code in other files you create will not be found when we grade your solution.
  • Each run must finish within 60 seconds of real time. Normal runs should only take a few seconds.

5.3 The player and what the viewer sees

The player works in the following way:

  • Each frame your receiver hands over with player.show goes to the back of the player's buffer.
  • Every 1/25 of a second (40 ms), the player takes the frame at the front of its buffer and shows it. If the buffer is empty, the frame already on screen stays there.
  • The player shows frames in the order it gets them. It will not reorder or skip a frame on its own.
  • Say the call starts at time 0. The camera, on the sender's side, captures frames at 0, 40, 80, 120, … ms. The player, on the receiver's side, refreshes and takes the next frame from its buffer at 40, 80, 120, 160, … ms. So a frame captured at time x has its last chance at the player's refresh at x + 200 ms: it is shown in time if, by then, it is the next frame in the buffer, even if your receiver hands it over at that very moment.

When and whether to hand a frame to the player is up to your receiver. It can hand a frame over the moment it is received, hold it back and hand it over later, or never hand it over at all.

How the simulator classifies each frame. The simulator knows when each frame was captured, and when it is shown to the viewer. It classifies each frame as one of the following:

  • Shown in time: on screen within 200 ms of being captured.
  • Shown late: on screen, but more than 200 ms after being captured (i.e., a lag).
  • Not shown: never on screen during the call, for example because it was never handed to the player.

5.4 The score

The simulator gives you a score for the call. The score has three parts.

Quality. Quality is computed as the average quality over all the frames of the call. For each frame, the quality is (level + 1) / 4 if the frame was shown in time, and 0 otherwise. So a frame shown in time at level 3 is worth 1, and at level 0 is worth 0.25.

Glitches. A glitch is a moment when the player shows something the viewer should never see:

  • a frame whose bytes do not match the frame at any of the four levels (the network never corrupts packets, so this only happens if your code puts a frame together wrong);
  • a frame shown again after it was already shown;
  • a frame older than one already shown, so the video jumps backwards.

Glitches are counted separately from how frames are classified. For example, if your receiver hands frame 10 to the player twice, frame 10 is classified by its first showing, and the second showing is a glitch. The glitch fraction is the number of glitches divided by the number of frames in the call.

Freezes. When the player has nothing new to show, the frame already on screen stays there. Missing one or two frames is hard to notice, but missing several in a row is a visible freeze. We use the definition of a freeze from WebRTC, the technology most video calls are built on:

  • Normally, a new frame appears every 40 ms. The picture is frozen when no new frame appears for at least 150 ms longer than that, so for at least 190 ms. At 25 frames per second, this happens when the player has nothing new to show 4 or more times in a row.
  • A freeze lasts from the moment the last new frame appeared until the next new frame appears. A glitch does not count as a new frame. For example, if a new frame appears at 1000 ms and the next one at 1300 ms, the picture was frozen for 300 ms. The freeze time of the call is the total length of all its freezes.
  • The freeze fraction is the freeze time divided by the length of the call. Here the call is measured from 200 ms after the first frame is captured to 200 ms after the last frame is captured. This includes the start of the call: if the first frames take too long to reach the screen, that counts as a freeze too.

Putting the three parts together:

score = quality − 5 × glitch fraction − freeze fraction

A perfect call scores 1, and a call that never starts scores −1. Glitches count five times: showing one frame at the wrong moment costs as much as losing five frames at the highest quality.

5.5 Scenarios and the baseline

The practice scenarios in scenarios/ cover different kinds of network conditions during a call, e.g., random loss, heavy loss, bursts of loss, reordering, a low rate, a rate that drops, rises or keeps changing during the call, a delay that jumps during the call, and a mix of these. You can open these files yourself to see each scenario's settings, but you cannot open and read them in your code. We grade your solution both on these scenarios and on hidden scenarios that are conceptually similar.

The baseline solution in the starter code works in the following way:

  • Quality: the sender picks the highest level that fits within the starting rate, and never changes it.
  • Sending: it splits each frame into packets and sends each packet once.
  • Receiving: it hands a frame to the player as soon as all its packets arrive.

The baseline never recovers anything that is lost and never reacts to the network. It is only meant as a starting point.

Output and logs. After every run, sim.py prints how joining and setup went, the score, how many frames were shown in time, shown late or not shown, how many were shown at each quality level, the lag from capture to screen, the glitches and freezes, and, for debugging, how many packets were sent in each direction and how many were lost or dropped waiting in line. It also writes these files:

  • logs/<scenario>-<name>.json: what was on screen at every moment of the call.
  • logs/<scenario>-<name>-packets.csv: every packet, with when it was sent, in which direction, its size and first byte, and whether it arrived (and when), was lost, or was dropped waiting in line. You can open it in a spreadsheet.
  • history.csv, next to sim.py: a record of all your runs. Each line includes when the run happened, which scenario and test files were used, the score (or that the run stopped with an error), and some information about your code. Keep this file and submit it with your solution (Section 8).

<name> is the name of the folder the call.py you ran is in: baseline when you run the baseline, and the name of your assignment folder when you run your own code. replay.py turns one or more of the first kind of log into a page that plays the video the viewer saw in each run, side by side, so you can see where your solution freezes or glitches and how it compares with another run. For example, if your assignment folder is named code, as in the starter code:

9. Frequently asked questions

Can my code print things, for example to debug? Yes. Your code can print to standard output or standard error. Printing does not affect the simulation or your score.

Should get_passcode wait until the join server closes the stream? No. Return as soon as you have the join server's whole reply.

How do I set a timer to call one of my methods? Pass the method to the timer, without calling it: clock.set_timer(100, self.resend). The simulator will call self.resend when the timer expires. A common mistake is to write clock.set_timer(100, self.resend()), which calls self.resend right away and passes its result to set_timer.

How do I check a packet's first byte? pkt[0] gives the first byte as an int, so you can compare it with a number, for example pkt[0] == 0x01. pkt[:1] gives the first byte as a bytes object of length 1, so you can compare it with bytes, for example pkt[:1] == b"\x01". A common mistake is to compare pkt[0] with b"\x01". This is always false, because an int is never equal to a bytes object, and Python does not raise an error to warn you.

Where can I learn about bytes and how to work with them? Check the Python documentation for bytes and bytearray, the struct module for turning numbers into bytes and back, as the baseline does for its header, and str.encode and bytes.decode for turning strings into bytes and back.

What type is frame.time? A float, in ms, not an int.

Does the time spent joining and setting up the call count against my score? No. The camera starts when the call starts, so no frames are missed while joining and setting up. What matters is that the call starts within 5 seconds.

Is the rtt_ms given to my code one-way or round trip? Round trip. It is the propagation delay to the other side and back. The link propagation delay described in Section 2 is half of rtt_ms at the start of the call. It does not include the time to transmit a packet, the time it waits in line, or jitter.

Is the passcode a string or bytes? A string of letters and digits: get_passcode returns it as a str, and it is given to your setup classes as a str. In the join server's reply and in JOIN, the passcode is represented as a bytes object: the ASCII bytes of the string.

Should my ReceiverSetup stop sending JOIN if the passcode is wrong? It does not need to. With a wrong passcode, the call should never start, and the simulator stops the run after 5 seconds. When sim.py runs a test file with a wrong passcode, it tells you whether your code behaved correctly.

Do rate_kbps and rtt_ms change during the call to reflect the current rate and RTT? No, they only represent these values at the start of the call. The link's rate and delay can change during the call, so you will need to measure them if you want to have the current values.

What does kbps mean? Kilobits per second, where a kilobit is 1000 bits.

Is there a limit on how many packets my code can send, for example acknowledgements or retransmissions? No, but if you send more packets to the link than it can carry at that moment based on its rate, the packets will have to wait in line, and may get dropped if the line gets too long (Section 2).
